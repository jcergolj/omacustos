    Default incremental backups (#62)¶

    Validation status: local correctness, measurement, Standards, and Spec gates passed; accepted for commit. The source now routes fresh normal-worker runs to v4 incremental storage. No installed service, cloud account, package, or deployment has been changed by this work.

    The earlier validation report records preparatory measurements and the blockers that existed before this integration. It is not the current implementation status or final delivery evidence.

    Ownership and upgrade¶

    • A locally created configuration is bound to the machine's stable OS identity and the fixed absolute configuration directory. Writer UUIDs and epochs are persisted before remote initialization; hostnames and editable set names are not writer identity. Namespace IDs for historical non-UUID set IDs are deterministic, so losing local settings cannot create an unrelated replacement namespace.
    • A verified-empty set can be provisioned automatically by a locally bound configuration. A nonempty or foreign repository is never silently adopted.
    • Imported, copied, and old unbound configurations are read-only. For an old pre-ownership configuration, use Offline writer takeover… once to enroll its verified-empty v4 namespace. This is ownership enrollment, not a format opt-in: there is no user-selectable full-upload mode for fresh runs.
    • Before confirming enrollment/takeover, stop the previous writer's processes, schedules, retries, and access permanently. An in-place upgrade must stop the old executable; any subsequent service invocation must use the new writer. The protocol is manual-offline, not a server lease or a fencing guarantee.
    • Existing remote ownership requires an explicit epoch-changing offline takeover. A durable handoff intent makes a lost response retryable. Restoring copied local state does not itself restore write authority.
    • An unfinished legacy copy resumes in its recorded format and exact namespace, after ownership enrollment where needed. Only a fresh run uses the new default.

    The first v4 run uploads a fresh baseline and does not reuse legacy payloads. Before publication work, the worker reports selected uncompressed source bytes plus the discovered existing-history payload size (or explicitly unknown size). Compression, manifests, and metadata change actual use; these are estimates, not quota guarantees. No history is removed to make room for the baseline.

    Saved states, checks, and integrity¶

    All selected regular files are hashed. Intentional skipped links/special nodes do not invalidate readable regular files. Missing roots, inaccessible directories, enumeration failures, and unreadable selected files are not treated as deletions. Execution prunes excluded trees instead of traversing them for preview data. Durable journals are placed outside selected roots. Volatile application queues, locks, and private coordination state are excluded and shown excluded in Preview; the actual settings file remains eligible, so configuration/home selections do not recursively capture a backup's own changing control state.

    New/changed regular files are uploaded whole. Renames and deletions reuse unchanged content. An unchanged check publishes no snapshot and consumes no retention slot. Run details distinguish the last successful check from the last saved change and expose integrity and historical-damage information.

    New uploads retain full verification and manifest-last publication. Reused objects retain original verification evidence and daily existence/size checks; those lightweight checks can miss same-sized corruption. Scheduled full integrity checking and verified restores remain necessary. Uploading replacement objects for a new state does not repair older snapshots; affected history is reported.

    Capture is file-by-file, not an atomic filesystem/application snapshot. Whole-file edits retransmit the whole file. Partially live immutable archives retain obsolete members; compaction and block-level deduplication remain out of scope.

    Cleanup and mixed history¶

    The normal history browser discovers and verifies both legacy copies and shared snapshots without requiring a local manifest cache. Old non-UUID IDs and legacy computer/set-name namespaces are associated with the configured set before retention planning. A shared snapshot cannot be deleted with the old whole-copy delete action.

    Scheduled backups do not authorize their own cleanup. When retention needs work, the UI reports cleanup needs attention. Choose Review incremental cleanup… and review the exact proposed snapshot, legacy-folder, and unreferenced-object identities. Confirmation authorizes only that proposal. A changed scope requires a fresh review.

    Cancelling a preview writes a dismissal, not deletion authority. A crashed/closed preview is recovered similarly before the next writer runs. Already-authorized interrupted cleanup resumes only its durable exact scope. Dismissed proposals cannot retire snapshots or authorize deletion. Retained and resumable references still block object deletion, and unreadable history still fails closed.

    The newest-N policy counts saved states across old/new formats. Unchanged checks do not evict history. Saved snapshots survive failed cleanup. Ownership, backup, integrity maintenance, and cleanup continue to serialize their mutations.

    Local performance evidence¶

    Build Release and run the repeatable, local-only matrix from disk-backed storage:

    cmake -S native -B /tmp/opencode/omacustos-62-release -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/opencode/omacustos-62-release --target incremental-benchmark staging-observer -j 4
python3 native/tests/run_incremental_benchmarks.py /tmp/opencode/omacustos-62-release/incremental-benchmark /tmp/opencode/issue62-measurements --bytes 536870912 --files 2048 --observer /tmp/opencode/omacustos-62-release/libstaging-observer.so

    The matrix separately compares v3 full uploads and v4 first/unchanged/small-edit runs, full/selective restores, cleanup, and retained-state restore. Profiles are unmodified current-repository source/QML/docs, an explicitly amplified version of that corpus, and deterministic mixed compressible/pseudorandom data. None is a customer workload or a cloud throughput measurement. Generated fixture contents are independently hashed and restored files/counts are checked.

    JSON evidence includes provider operation counts/times, transfer bytes, boundary intervals, dedicated local-plan/hash, capture, compression, publication and verification measurements, boundary samples, and event-observed private staging peaks. The observer accounts for regular-file write growth, truncation, removal, and open unlinked writers; provider-boundary synchronization covers kernel copies/reflinks. The successful serial fixtures do not release bytes between a provider copy and that observation. A unit test checks its accounting and a smoke case requires that it never underreport known boundary samples. Provider times overlap phase times and must not be added to them. Staging samples are logical file bytes, not allocated filesystem bytes or a universal process high-water mark. Restore temporary workspaces are disk-backed; destination trees and their final atomic-placement temporary files are outside the reported private workspace scope. Diagnostic observer overhead is included in these local timings. The matrix uses the production 1 GB staging budget and 1,000-file cap, not the unconstrained budgets of the earlier sizing probes.

    Approximately 106 GB was available before the matrix. The conservative fixture guard alone needs 160 GB for a 20 GB input; 20/50/100/500 GB fixtures are therefore not practical here. No cloud measurements were authorized or performed.

    Final local execution evidence — 2026-10-21¶

    cmake --build build -j 4 succeeded. A clean, single invocation of ctest --test-dir build --output-on-failure -j 2 passed 41/41 suites in 427.15 seconds. Existing timeouts were not increased and no cases were dropped. An earlier full invocation exposed historical CLI fixtures that still assumed the old default. Explicitly selecting their historical test seam fixed those fixtures; all their assertions remain intact. New default-process tests never use that override.

    Release benchmark smoke validation passed 3/3. The controlled matrix above then completed 18/18 invocations, two repeats for each profile/target, with no concurrent build/test load. Every invocation checked old/new and selective restored bytes/file counts, unchanged no-payload/no-snapshot behavior, exactly one edited-file archive, preview-without-deletion, exact cleanup confirmation, and a byte-verified retained restore. The v4 first-run timing includes initialization; all v4 runs include source enumeration and full local planning/hashing.

    Environment: local disk-backed Btrfs, Intel i5-9600K (6 cores), GCC 16.2.1, Qt 6.12.0, libarchive 3.8.10, zlib 1.3.2, Release optimizations. All remote operations used private LocalProvider fixtures. Its metadata inspection hashes files internally even when the exposed checksum is withheld. No CLI startup, network, encryption, service quota, cloud throughput, or production speedup is being measured. The small real repository corpus is slower with v4's fixed control/verification overhead; the larger profiles reduce repeated payload work but have a slower, more thoroughly verified first baseline than v3.

    Archive-target decision¶

    Retain the approximately 1 GB uncompressed requested target, together with the existing 1 GB staging budget and 1,000-file limit. This is a measured choice for the normal configuration, not a promise of 1 GB compressed archives:

    • Production constraints already limited the amplified/mixed v4 baseline to three objects at both 256 MB and 1000 MB. Moving to 256 MB saved only about 2.4% of mixed private-peak/selective-transfer bytes in this trace, with no consistent repeat-level timing advantage.
    • A 64 MB target reduced selective-transfer cost substantially, but raised v4 baseline calls from 122 to 230 and objects from three to nine. It did not reduce observed obsolete member bytes in these edit/delete traces.
    • The small unmodified repository used one object at every target. Fixed verification/control overhead dominates there; no target choice made v4 faster than v3 in that local case.

    The default therefore prioritizes fewer remote operations while preserving bounded, fully verified capture. Different latency, selection, file-size and change-rate distributions can favor smaller groups; users must not interpret these local fixtures as measured cloud throughput or a universal optimum.

    Pre-commit review record¶

    Separate Standards and Spec reviewers rechecked the integration. Blocking findings were resolved with regressions: skipped-link handling, abandoned cleanup previews, takeover after legacy cleanup, configuration/journal overlap, exact confirmation after legacy resume, and the integrated failure matrix. Both final source re-reviews found no remaining verified blockers. Both final acceptance reviews independently verified the 18 raw evidence files and receipt, approved the documented scope/limitations and archive-target decision, and found no remaining blockers for commit/issue closure after delivery to master. This work does not authorize deployment.
