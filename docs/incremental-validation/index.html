    Incremental validation and rollout gate (#62)¶

    Historical preparatory report, preserved as evidence. Current integration and validation status are tracked in Default incremental backups.

    Status: not ready for default rollout. This validation work does not close #62. The normal worker still creates full v3 archive copies. No opt-in release, default switch, compression change, cloud access, or deployment is part of this change.

    Reproducible local benchmark¶

    Build the real core implementation with Release optimizations:

    cmake -S native -B /tmp/opencode/omacustos-62-release -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/opencode/omacustos-62-release --target incremental-benchmark -j 4

    From a writable disk-backed working directory, run:

    /tmp/opencode/omacustos-62-release/incremental-benchmark 1073741824 4096 64000000 documents-code
/tmp/opencode/omacustos-62-release/incremental-benchmark 1073741824 4096 256000000 documents-code
/tmp/opencode/omacustos-62-release/incremental-benchmark 1073741824 4096 1000000000 documents-code

    Repeat with mixed for deterministic half-code/half-pseudorandom file content. Arguments are selected bytes, file count, uncompressed archive target, and profile. Fixtures are synthetic, not a representative customer corpus. Seeds and source generation are fixed; identities/timestamps vary. Each invocation creates and removes its own private local fixture, and requires eight times the selected bytes free as a conservative fixture capacity check. It never uses Proton or a configured backup root. Compression stays tar.gz with the production defaults. The fixture uses a staging budget of at least four times the archive target and raises the file-count limit to the fixture file count, so those constraints do not silently cap the sizing comparison. This is not a measurement of the normal 1 GB staging budget or 1,000-file group limit.

    JSON lines record these scenarios separately:

    • Fresh v4 baseline; unchanged check; small edit plus rename and deletion.
    • Full restore of both old and new states after hiding local coordination state.
    • Single-file restore of an unchanged file from its original archive, rather than the small new archive containing the edited file. Select the middle logical path to avoid biasing the result toward a short final archive.
    • Exact-proposal preview/confirmation and cleanup down to one saved state.
    • Full restore of the retained state after cleanup.

    Independent SHA-256 fixtures and exact output file counts check every restore. An unchanged check must publish no manifest and upload no objects. Renames and deletions must not retransmit unchanged payloads: only the edited file is packed. Cleanup must require confirmation, perform no deletion during preview, and leave exactly the intended newest snapshot. Two tiny CTest smoke cases cover both fixture profiles; timings are never gates.

    Measurement boundaries¶

    • Total scenario time excludes fixture generation, independent expected hashes, and post-restore comparison. Restore time includes discovery/verification and placement. Cleanup includes proposal, confirmed execution, and readback discovery.
    • boundary_intervals_ns sums time since the preceding durable checkpoint into the named ending boundary. planned/capturing includes scan/hash work. Preparation/capture and compression span preparing, prepared-sources, and prepared-local: packing also emits control polls, so these cannot isolate compression CPU time. uploaded and object-verified include transfer/verification and ordering overhead. Repeated boundary names accumulate. These are not exclusive CPU subphase measurements.
    • Provider operation counts and nanoseconds measure individual local calls; they overlap boundary/wall times and must not be added to them. Uploaded and downloaded bytes count successful local transfers, including control metadata. They do not measure failed partial transfers or network wire overhead.
    • The provider withholds checksums to exercise download/hash verification, but delegates metadata inspection to LocalProvider, which hashes internally. Consequently even unchanged runs include extra local reads. No CLI startup, encryption, network latency, rate limiting, or real quota behavior is measured.
    • checkpoint_sampled_writer_staging_peak_bytes is a lower-bound sample at checkpoints and provider boundaries, not an exact high-water mark. It excludes restore staging, source/restore trees, and independent member extraction space. Frequent capturing/preparing control polls do not walk staging; doing so would add quadratic measurement overhead as the file group grows.
    • Inventory records distinguish compressed referenced archive bytes from total physical/obsolete uncompressed member bytes in the newest snapshot. Obsolete member bytes are not reclaimable compressed bytes, nor necessarily obsolete across retained history. Shared archives are not compacted.
    • These probes do not compare to fresh v3 full backups, isolate scan/hash from journal overhead, or provide authorized-cloud or large-corpus evidence.

    Remaining release blockers¶

    1. Integrate stable local computer identity and repository ownership with normal backup-set creation, worker scheduling, queue pause/cancel/resume, and recovery. Imported/restored configurations must remain read-only until explicit takeover; never silently initialize a new writer over existing history.
    2. Scan the configured roots/inclusions/exclusions into complete source mappings; preserve scan failure as a failure, not a deletion. Preserve the durable format of interrupted legacy copies rather than converting them during resume.
    3. Surface first-baseline capacity estimates/warnings (old history plus new baseline), distinct successful-check/saved-change/integrity status, cleanup attention, and mixed-format history in normal worker/UI paths.
    4. Integrate newest-N retention with exact deletion authorization. The advanced executor requires explicit per-proposal confirmation; do not bypass that safety protocol just to make scheduled cleanup automatic.
    5. Add worker/GUI end-to-end failure-injection tests for these integration paths. Existing advanced-executor tests alone do not prove the default upgrade path.
    6. Gather representative sizing evidence, including v3 comparison, repeats, larger corpora where practical, and accurate staging/subphase instrumentation. Select the production target only from sufficient evidence. The current approximately 1 GB target remains unchanged; that is not a measured selection or a performance promise.

    Whole-file edits require whole-file retransmission. Capture is non-atomic, file-by-file, not an application-consistent filesystem snapshot. Lightweight existence/size reuse checks may miss same-size corruption until a scheduled full integrity check or restore. A partially live archive retains obsolete members. No benchmark authorizes weakening verification, retained-history protection, publication ordering, exact-scope deletion, or offline ownership handoff.

    Execution environment (2026-10-20)¶

    Core base: ae7a9207df1956896a1dd6ad49cbef375780d94d; only the benchmark and CMake test registration are added to that implementation. Host: Intel i5-9600K, 6 cores, GCC 16.2.1, Qt 6.12.0, libarchive 3.8.10, zlib 1.3.2, Release -O3. Fixtures run on the local Btrfs SSD mount with filesystem compression enabled. Reported file/tree bytes are logical file sizes, not allocated disk space. These are exploratory runs, not repeated performance measurements or default-selection evidence. Earlier runs with per-read staging-tree sampling were discarded: that probe disproportionately slowed larger file groups and was corrected before recording final measurements.

    Approximately 100 GiB was available. The conservative eight-times fixture guard requires 160 GB for a 20 GB selected corpus; therefore 20/50/100/500 GB runs were not practical on this filesystem and were not attempted. No cloud measurements were authorized or performed.

    Pre-commit independent reviews covered standards and #62 separately. Both found the archive-upload-count assertion insufficient; it now checks the sole newly uploaded archive member's size and SHA-256. The standards review additionally requested exact post-cleanup snapshot enumeration, now asserted before retained restore. Both re-reviews found no remaining blockers in this preparatory scope, while the spec review explicitly retained the default-rollout blockers.

    Automated test results¶

    • cmake --build build -j 4 succeeded.
    • ctest --test-dir build --output-on-failure -j 2: 29/30 suites passed; workerrecovery-test reached its existing 180-second timeout during concurrent benchmarking, with no assertion failure reported before timeout. This was not a clean full-suite run.
    • After stopping benchmark load, ctest --test-dir build -R '^workerrecovery-test$' --output-on-failure: 1/1 passed in 176.33 seconds. The narrow timeout margin remains a test-budget concern; no timeout, integrity, or recovery behavior was changed to get a pass.
    • Final Release rebuild and ctest --test-dir /tmp/opencode/omacustos-62-release -R incremental-benchmark --output-on-failure: 2/2 passed, also independently rerun by both reviewers.

    All 30 suites passed across those invocations, not together in one clean run. These results do not remove the rollout blockers above.

They remain in partially live archives even after newest-one retention; the renamed file is reused. This small fixture does not establish long-term obsolete-data behavior or reclaimable compressed space.

    The tradeoff is visible: larger groups reduce calls, while selective restore of one unchanged 262,144-byte file downloads substantially more data. Compressed baseline sizes barely vary on these fixtures. These single synthetic runs cannot choose a production target: keep the current target unchanged pending the representative/repeated/cloud and exact-staging evidence described above.
